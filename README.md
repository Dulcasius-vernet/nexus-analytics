# Nexus Analytics

**AI-augmented business intelligence and predictive analytics platform**  
Prototype prepared for the Npontu Technologies Intelligent Systems Services Engineer practical assignment.

Nexus Analytics demonstrates a business-to-insight workflow: business onboarding, workspace creation, synthetic or CSV data ingestion, PostgreSQL analysis, machine-learning evaluation and inference, Snwolley-assisted interpretation, and management reporting.

The initial demonstration use case is transaction-risk analytics using a reproducible synthetic Ghanaian mobile-money dataset. The application records a configurable business objective during onboarding and keeps the business/workspace model separate from the demonstration use case. The current productionised ML pipeline is specifically a fraud-risk classifier; other objective types are captured but do not yet have their own trained model pipelines.

## Implemented capabilities

- Business registration and sign-in with PBKDF2 password hashing and signed, expiring HTTP-only session cookies.
- Business membership and business-scoped API access; attempts to query another business are rejected.
- Automatic creation of a business, default workspace and initial analytical objective during registration.
- Additional workspace creation and listing.
- PostgreSQL 16 relational schema for users, businesses, memberships, workspaces, analytical objectives, datasets, customers, agents and transactions.
- Composite business-scoped keys for customers, agents and transactions, allowing source identifiers to be reused safely by different businesses.
- Idempotent schema initialisation and migration logic for earlier single-column primary keys.
- Reproducible 30,000-record synthetic data generation and tenant-scoped sample-data loading.
- CSV upload, validation, bulk loading and data-quality checks.
- SQL analytics using joins, filters, aggregations, CTEs, window functions and conditional aggregation.
- FastAPI endpoints for KPIs, transaction records, weekly trends, transaction types, channels, regional summaries, data quality and datasets.
- Scikit-learn preprocessing and Random Forest classification, compared with a DummyClassifier baseline.
- Model metrics served from the saved training run and a batch-capable inference endpoint.
- Interactive dashboard charts for weekly trends, transaction types and channel distribution.
- Server-side Snwolley Agent integration for contextual business questions and AI-assisted management reports.
- PDF generation for the AI-assisted report.
- Structured backend error responses, configuration through environment variables and automated tests.

## Important limitations

This is an assignment prototype, not a production-ready financial-crime detection service.

- The bundled dataset is synthetic and does not represent an actual mobile-money operator or real customer behaviour.
- The fraud labels are generated by an artificial risk mechanism; they are not verified fraud cases.
- The current ML pipeline is a fraud-risk example. Other business objectives can be selected and stored, but separate forecasting, lead-scoring or segmentation pipelines are not implemented yet.
- The model has limited discrimination and low precision. Its scores are not calibrated probabilities and must not be used as standalone fraud decisions.
- Workspace creation is implemented, but fine-grained role administration, invitations, password reset, email verification and account recovery are not.
- The Snwolley API integration is implemented, but live provider connectivity requires a current valid API key in the local environment.
- Database-backed integration tests require a running PostgreSQL service. Tests are automatically skipped when PostgreSQL is unavailable.
- Production model monitoring, drift alerts, scheduled retraining, distributed rate-limit queueing and deployment hardening remain future work.

Do not use real customer data or expose this prototype to the public internet without a full security and privacy review.

## Prerequisites

- Python 3.11 or later (use a version supported by the pinned dependencies).
- Node.js 20 or later.
- Docker Desktop / Docker Engine with Docker Compose.

## 1. Configure the environment

From the project root:

```powershell
Copy-Item backend/.env.example backend/.env
```

Generate a strong session signing secret:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Put the generated value in `backend/.env` as `SESSION_SECRET`. Set `SNWOLLEY_API_KEY` to a current key supplied for the assignment. Never commit `backend/.env`, place the key in a `NEXT_PUBLIC_` variable, or expose it to the browser.

The local database credentials in `.env.example` and `docker-compose.yml` are development-only. Change them before using any shared environment. In production, use a strong unique `SESSION_SECRET`, set `APP_ENV=production` to enable secure cookies, and use managed secret storage.

## 2. Start PostgreSQL

From the project root:

```powershell
docker compose up -d db
docker compose ps
```

The service uses PostgreSQL 16 and a persistent Docker volume named `nexus_pgdata`.

## 3. Initialise the backend

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m scripts.init_db
python -m uvicorn app.main:app --reload --port 8000
```

The API documentation is available at http://localhost:8000/docs. The public API health endpoint is `GET /api/v1/health`; database readiness is `GET /api/v1/health/database` and requires an authenticated session.

## 4. Start the frontend

Open a second terminal from the project root:

```powershell
cd frontend
npm install
npm run dev
```

Open http://localhost:3000.

The frontend proxies `/api/backend/*` to FastAPI at port 8000. Session cookies are HTTP-only and are not readable by frontend JavaScript.

## 5. Create a business workspace and load data

1. Select **Create account**.
2. Enter your name, email, password, business name, industry, workspace name and initial business objective.
3. The backend creates the user, business, membership, workspace and objective in one database transaction.
4. Open **Data management** and select **Load synthetic demo dataset** to load the bundled 30,000-row sample into your own business, or upload a compatible CSV.
5. Use the Overview, SQL analytics, Machine learning and AI reports sections to explore the workflow.

The demo dataset endpoint is tenant-scoped. Re-loading the same transaction identifiers into the same business returns a conflict rather than duplicating records. Composite primary keys permit the same source identifiers in a different business.

## 6. CSV transaction format

CSV uploads are limited to 25 MB and must include the following required columns:

- `transaction_id`
- `business_id` (required by the validator; the backend assigns the authenticated business ID on ingestion)
- `customer_id`
- `agent_id`
- `transaction_ts`
- `transaction_type`
- `amount`
- `is_fraud`

Optional model and quality fields include `channel`, `device_age_days`, `failed_attempts_24h`, `customer_tenure_days`, `hour_of_day` and `risk_reason`. The current model expects these feature columns; missing optional values are imputed by the saved preprocessing pipeline.

## 7. Generate data and train the model

From `backend` with the virtual environment active:

```powershell
python -m scripts.generate_data
python -m scripts.train_model
```

Training writes:

- `backend/artifacts/fraud_risk_pipeline.joblib`
- `backend/artifacts/metrics.json`

The training script uses a stratified holdout set, a DummyClassifier baseline, ROC AUC, average precision, classification metrics and a threshold selected to maximise holdout F1. The threshold is not a universal operating point and should be selected against business costs, review capacity and validation data in a real deployment.

Latest saved holdout metrics for the bundled seed:

| Metric | Result |
|---|---:|
| ROC AUC | 0.6268 |
| Baseline ROC AUC | 0.5000 |
| Average precision | 0.0320 |
| Baseline average precision | 0.0207 |
| Selected threshold | 0.1267 |
| Precision at threshold | 4.08% |
| Recall at threshold | 26.45% |
| F1 at threshold | 0.0707 |
| Predicted-positive rate | 13.40% |

These figures indicate modest ranking improvement over the baseline but low precision. The application labels outputs as risk scores and review flags, not confirmed fraud decisions.

## 9. Snwolley Agent integration

The backend sends aggregate business metrics, transaction-type/channel summaries and saved model evaluation metrics to Snwolley. Individual customer or transaction rows are not intentionally included in the AI report context. The API key is read from `SNWOLLEY_API_KEY` on the server and is never sent to the browser.

The assignment specification states a limit of five requests per minute. HTTP 429 responses are surfaced with the provider's `Retry-After` value; the current implementation does not run a distributed request queue. AI-generated text is advisory. Verify its claims against the underlying aggregates and do not treat it as evidence or as an automated fraud decision.

## 10. Tests and integration checks

Run the automated tests:

```powershell
cd backend
python -m unittest discover -s tests -p "test_*.py" -v
```

Database-dependent tests run only when PostgreSQL is available. They are skipped otherwise; a skipped test is not a successful database integration test.

For an explicit live integration check, configure a valid `DATABASE_URL` and a fresh `SNWOLLEY_API_KEY` in `backend/.env`, start PostgreSQL, and run:

```powershell
$env:RUN_LIVE_INTEGRATION_CHECKS = "1"
python -m scripts.live_integration_check
```

This opt-in script checks the database/schema and sends one small connectivity request to Snwolley. Do not run it repeatedly because the provider has a five-requests-per-minute limit.

## 11. Security and operational considerations

- Passwords are hashed with PBKDF2-HMAC-SHA256 and random salts.
- Sessions are signed, expire after 12 hours and use HTTP-only, SameSite=Lax cookies.
- Business-scoped API access is verified against active user membership on each request.
- Customer, agent and transaction identifiers are scoped by composite business keys.
- SQL parameters are bound rather than concatenated from user input.
- Snwolley credentials remain server-side and are supplied through environment configuration.
- The demo database password and fallback session secret are development defaults only.
- There is no email verification, password reset, account lockout, fine-grained invitation workflow or production-grade audit trail yet.

## 12. Assumptions and future improvements

- The first use case is mobile-money transaction-risk analysis; additional business problem types require their own schema mappings, feature pipelines, evaluation criteria and inference contracts.
- The synthetic fraud mechanism is intentionally transparent and not calibrated to a provider's actual fraud rate.
- The current model should be improved using more informative behavioural features, time-based validation, calibration, threshold/cost analysis and stronger precision-recall performance.
- Larger or streaming workloads could use scheduled ingestion or Kafka, a queue-backed training service, model registry/versioning, Elasticsearch for search/observability, and Prometheus/Grafana for operational monitoring.
- Before production, implement rate limiting for authentication, CSRF protection appropriate to the deployment, stronger secret management, audit logging, database migrations with a migration tool, backup/recovery, monitoring and a full penetration/privacy review.
